# Pipeline, project, detection and discovery

Reference for the modules directly under `src/` (no `CLAUDE.md` loads for them): `pipeline.ts`, `project.ts`, `projectLocation.ts`, `detectPackageManager.ts`, `discovery.ts`, `commandRunner.ts`, `stepError.ts`. Read it before changing any of them, or how a member run, detection or discovery behaves. Nothing imports it.

## Pipeline (`src/pipeline.ts`)

`src/pipeline.ts` runs detect → discover → plan → apply → report once for every manager. Discovery is `discoverFromRegistry` (`src/discovery.ts`) for every manager, yarn berry included since #107: no manager subprocess, it reads the manifests, the installed versions (`node_modules`, or the lockfile an adapter's `installedFromLockfile` names: npm's `package-lock.json` without `node_modules`, berry's `yarn.lock` always) and the registry reader. Discovery is not an adapter concern: no adapter parses a manager's `outdated`.

- `check(project, { next? })` - Returns `Record<string, PackageInfo>` of outdated packages, keyed by package.json name, and prints them: it plans them first, so the human report shows what `update` would do with each and why
- `findOutdated(project, targets?)` - Discovery alone, no report: no plan, so no per-version manifest is read. `check --json`, `update --dry-run` and interactive run it, then `plan`. A named package no manifest the run reads declares fails with a `discover` `StepError` (`<name> isn't a dependency of this project`) before the header or any lookup
- `plan(project, outdated, targetPackages?)` - The policy's `UpdateResult[]` (dry-run, interactive). It runs `src/utils/filterPackages.ts` with `project.config` and `adapter.overrides(root)`
- `update(project, { targetPackages?, discovered? })` - Plans, applies, returns `UpdateResult[]`. `discovered` is a `check` result the caller already has, so discovery is not run twice. After apply, each moving dependency is checked against what the manager installed (`src/utils/installed.ts` reads `node_modules`; an adapter with `installed()`, yarn berry under PnP, answers from the manager instead): one the manager left below its target is reported `updated: false`, reason code `not-applied`, `not applied by <pm> (installed <version>)`
- `refuseMemberApply(project)` - See Member runs

## Project (`src/project.ts`, `src/projectLocation.ts`)

`openProject(cwd, { pm?, cache? })` builds the `Project` (`{ root, member?, config, adapter, registry }`) once per command run: `locate(cwd)` (`src/projectLocation.ts`: the nearest package.json's directory and the workspace root that lists it, package.json `workspaces` or the nearest pnpm-workspace.yaml when it lists it, before a manager is known), `loadConfig` (the member's own file, else the root's), then `logger.configure(config)` and the config's warnings, then detection (`adapterFor(detectPackageManager(workspaceRoot, pm, { from }))`), then `adapter.projectRoot(dir)` for the final `root` (a `member`, from `memberAt`, when that is not the directory itself). When that differs from the workspace root `locate` found, detection runs again there (a different manager is a `detect` `StepError`) and the config is reloaded with it as the fallback.

- The pipeline reads `project.config`; nothing below a command loads the config again
- Everything the pipeline runs or writes uses `root`
- `registry` is a lazy `RegistrySession` (nothing is read or loaded until it is used) whose `.npmrc` view is the manager's at `root`, where every manager command runs, whatever the cwd (#127); `check` and `update` close it in a `finally`. It is wrapped in `withReleaseAgeGate` (`src/utils/REGISTRY.md`)
- With no `package.json` in the cwd or any parent, `openProject` fails with `No package.json in <cwd> or any parent directory`

## Detection (`src/detectPackageManager.ts`)

`detectPackageManager(root, pm?, { from, cwd }?)`, first source that answers (`root` is the workspace root that lists the run's directory, `locate()` in `src/projectLocation.ts`; `from` the member's directory: the declaration is the nearest package.json from it up to `root` that declares a manager, so a member without one uses the root's, and a member's own beats the root's; lockfiles are always `root`'s; messages name declaring files relative to `cwd`, the command's directory, and the searched directory when it is not `cwd`):

1. `pm`: the `--pm` option
2. package.json `packageManager` (`pnpm@12.14.0+sha512.…`): the name before the first `@`
3. package.json `devEngines.packageManager`: one `{ name }` or an array of them. Of the supported names, the one with a lockfile present, else the first
4. The lockfiles: each adapter's `lockfile` (package-lock.json, yarn.lock, pnpm-lock.yaml, bun.lock), in registry order npm -> yarn -> pnpm -> bun, last match wins. With more than one, a warning names the choice

A `packageManager` naming an unsupported manager falls through to `devEngines.packageManager`; when every declaration names only unsupported managers (`deno@2.5.0`), the `detect` step fails rather than guessing from a lockfile. Lockfiles that disagree with the chosen manager are logged at debug level as ignored, unless the declared manager has no lockfile while another has, which warns. A `--pm` that contradicts a declaration warns (Corepack may refuse it). The choice itself is logged at debug level. With nothing declared and no lockfile, `detect` fails and suggests `--pm`. A declared manager with no lockfile is used. `adapterFor(name)` returns the adapter.

## Native discovery (`src/discovery.ts`)

No subprocess: `check`, and `update`'s discovery, read the manifests, `node_modules` and `RegistrySession.lookup`. The same rules for every manager:

- **Declared:** `dependencies`, `devDependencies`, `optionalDependencies` of the root and each member (`readDeclaredDependencies`, `src/utils/dependencySpecs.ts`), first field wins. A name only in `peerDependencies` is not discovered (npm and bun's `outdated` listed it; pnpm's and yarn v1's did not). A manifest that can't be read is a `discover` `StepError`
- **Specs:** `classifySpec` resolves `catalog:` through `Workspace.catalogs`; skips specs that never reach the registry (`workspace:`, git, file, link, URL and github shorthand; each with a debug line); looks an `npm:name@range` alias up by its target and keys the row by the manifest key, and a bare `npm:name` as the `latest` of that name (npm reads it so); follows `latest`; warns and skips any other dist-tag and an unknown catalog entry
- **Installed:** `readInstalledPackages` reads `node_modules`. A symlink or junction to a directory inside the project (a link: a workspace member) is skipped without a lookup, and so is any dependency named like a workspace member, whatever is installed (pnpm's injected workspace packages are real copies; an `npm:` alias to a registry package of that name is still looked up). A dependency not installed is a `current: 'missing'` row; a missing optional one is skipped. With a registry dependency declared and no `node_modules` in the root or in any manifest that declares one (pnpm with `sharedWorkspaceLockfile: false` installs per member), pnpm, yarn v1 and bun fail discovery with a `discover` `StepError` telling the user to run `<pm> install`. An adapter whose `installedFromLockfile(root)` returns a reader replaces both: the pipeline passes it as `readInstalled` with `requireNodeModules: false`, and logs which lockfile at debug level. npm's (#107) answers when the root has `package-lock.json` and no `node_modules` (`src/managers/npm/CLAUDE.md`); with node_modules, node_modules decides. Its `peers` (#232, `LockedInstall.peers`) stands in for `readInstalledPeers` in the plan's peer pass (npm's `readLockedPeers`, berry's `readBerryLockPeers`, only under PnP)
- **Versions:** from `RegistrySession.lookup`, one per unique name
- **`wanted`** (`PackageInfo.wanted`, the highest version the manifest range allows: `wantedVersion()`, `src/utils/wanted.ts`), per manifest, the same rule for every manager: an exact pin is its own; else `latest` if it satisfies the range and isn't deprecated; else the highest non-deprecated satisfying version; else the highest satisfying one. It can sit below `current` (a deprecated version installed); `src/utils/report.ts` then shows no in-range note. Nothing satisfying: `wanted` is `current` (and no note). It ignores `engines.node`, since discovery has no per-version manifests: npm's preference for a version its Node runs is applied in the plan (`src/utils/plan/CLAUDE.md`, #200). Berry skips the `latest` step (`prefersLatestInRange`, #107) and its release-age gate applies to every lookup (#166)
- **Listed** when `current` is `missing`, or `latest` or `wanted` is ahead of `current`. Single-package keys and workspace entries are sorted by name (workspace: then root first, then path)
- **Failures:** every lookup settles, then any `ok: false` becomes one `StepError('discover')` naming each package with its reason (the first 10, then "and N more"). Nothing is left out silently; a failed lookup fails the run (a quarantined lookup, #166, is left out with a warning)
- A workspace is folded by `foldWorkspaceEntries()` into one `PackageInfo` per name carrying `workspaces`. Discovery keeps the owning manifest of every outdated entry (`Discovery` in `src/managers/adapter.ts`); every `--json` row carries its `workspace` (the manifest's directory, `"."` for the root)
- Discovery reads every manifest (root and members) itself, so it needs no workspace flags and no subprocess. The flags (`-r` for pnpm, `--filter *` for bun) belong to apply's update commands only

## Installed versions (`src/utils/installed.ts`)

- `installed.ts`: `readInstalledPackages(cwd, rows, { links, declaredOnly })` returns `{ version, linked }` (resolves the project's real path once per call; `links: false` skips the link test and `linked` is always false, which is what `readInstalledVersions` and the post-apply check use; linked: a symlink or junction to a directory inside the project and outside node_modules, i.e. a workspace member; pnpm and bun store links are not). `readInstalledVersions(cwd, rows, { declaredOnly })` is its versions: each moving row's installed version (the pipeline uses an adapter's own `installed()` instead when it has one: yarn berry, PnP), keyed by `rowKey` (the name, plus `<workspace>:` in a workspace project), read from `<member>/node_modules/<name>` first, then the root's, only for names that manifest declares (`declaredOnly: false` reads any installed package, which the target-peer pass uses for peers, #198). `readInstalledManifests(cwd, rows)` reads the installed copy's package.json (license, #197) over the same scan, only a copy at the row's `current`. `checkApplied()`: rows the manager left in place become `not applied by <pm> (installed …)`; every row of a package with a cooldown fallback must be installed at exactly its target (#151)

## Member runs (#123)

From a workspace member, or a directory inside one, `openProject` sets `Project.member` and `Project.root` is the workspace root the manager treats as the project (`adapter.projectRoot(dir)`: npm, yarn v1 and bun, the nearest ancestor whose `workspaces` lists it; pnpm, the nearest `pnpm-workspace.yaml`'s directory when that file lists it, never a farther one; berry, the nearest directory with a `yarn.lock`, and it refuses with a `detect` `StepError` from a directory the root does not list). A pnpm directory with its own `pnpm-workspace.yaml`, or one no root lists, is its own project, not a member.

- `check` and `update --dry-run` then read the member's manifest only: `Workspace.member` (set by `workspaceOf(project)`) scopes discovery to that manifest, for every manager, berry included
- `update` from a member, `-i` included, is refused by `refuseMemberApply(project)` before anything is discovered, run or asked: every manager's install rewrites the lockfile all workspaces share and moves other workspaces' locked copies (npm's also leaves `node_modules` behind `package-lock.json`; yarn v1's lockfile is the workspace's; berry's `up` is project-wide), so a write is never scoped to a member, and it runs from the root
- The config is the member's own `.always-up-to-date.json`, else the workspace root's (`configFileFor`, no per-key merge)

## Command runner (`src/commandRunner.ts`, `src/stepError.ts`)

- `runCommand(packageManager, args, cwd, isSuccess?)` runs the manager with an argument array via `runProcess` (`src/utils/runProcess.ts`: `execFile`, no shell, no output cap) and returns stdout. Commands are always built as arrays, never strings (`['update', ...names]`); shell quoting such as `'*'` must not appear in arguments. All manager commands go through it
- Success is decided per call by a `SuccessCheck` over `{ exitCode, stdout }` (exit code plus parsable stdout); the default is exit 0. stderr is never a failure signal (yarn v1 on Node 24 always prints a DEP0169 warning); it is logged with `logger.debug`
- A failure throws `Command execution failed: <stderr, else stdout>`; a process with no numeric exit code (spawn failure, killed) throws the "unknown error" message. `runCommand` does not log failures; the command layer reports them once
- `runStep()` tags failures: the pipeline hands each adapter `run(args, { isSuccess?, manifestWritten? })`, bound to the step (`discover` or `apply`) and the manager, so a failure rethrows as a `StepError` (`src/stepError.ts`, step `detect` / `discover` / `apply`, plus `manifestWritten`). Pass `manifestWritten: true` when autd rewrote a manifest before the apply command (npm, pnpm, bun, berry; yarn v1 once it has written a member's beyond-range specs). yarn v1 otherwise writes its own manifest, so it passes `false`. Every command uses the default success check; there is no `outdated` to treat specially
- Nothing catches: failures reach `src/commands/reportFailure.ts`, which reports once and exits 1. Never catch and return an empty result
