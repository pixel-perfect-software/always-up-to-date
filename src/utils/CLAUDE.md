# Utilities - Component Context

## Purpose

Shared utilities for configuration management, update logic, registry/cooldown handling, logging, file operations, and package grouping.

## Current Status: Stable

Core utilities fully implemented. There is no barrel: import each module by its path (`@/utils/logger`).

## Component-Specific Development Guidelines

- Import leaf modules (`@/utils/logger`, `@/utils/runProcess`); `src/utils` has no barrel
- `runProcess(file, args, { cwd })` is the only way to start a subprocess: `execFile` with no shell and `maxBuffer: Infinity`. On Windows, where npm/pnpm/yarn are `.cmd` shims Node only starts through cmd.exe, it runs `buildWindowsCommand()` through the shell, double-quoting arguments that contain cmd.exe operators (the windows-latest CI jobs cover it: the `.cmd` shim test in runProcess.test.ts, realSubprocess.test.ts through `npm.cmd`, and the integration matrix against real npm, pnpm, yarn and bun on Windows)
- `runProcess` passes `env: process.env` explicitly; under Jest the sandbox env otherwise never reaches the child, so PATH-shim tests depend on it
- Config uses nullish coalescing with `DEFAULT_CONFIG` for safe merging
- Cooldown's network path (`releaseTimes`, npmrcLoader) never throws: a transient error leaves the times the lookup had (an empty map when it had none). The cooldown gate then holds the target as `release date unknown` (#139), since the freshest releases are the ones a lagging mirror lacks. The reader (`lookup`) does not: it reports each failure per package as `{ ok: false, kind, reason }` and the consumer decides. Don't "fix" it to return an empty or partial result, which would turn an outage into "no versions"

## Architectural Patterns

### Configuration (`config.ts`)

- Config file: `.always-up-to-date.json` in project root
- `loadConfig(workingDir?, fallbackDir?, onWarning?)` reads JSON, merges with `DEFAULT_CONFIG`. `configFileFor(workingDir, fallbackDir?)` is the file it reads: the working directory's own, else the fallback's, with no per-key merge. A member run (#123) passes the member's directory and the workspace root, so a member's file replaces the root's whole. Only `openProject` (`src/project.ts`) calls it for a command run; everything else takes the loaded config as a parameter. `onWarning` receives the unknown-key warnings: `openProject` collects them and prints them with `logger.warn` right after `logger.configure`, since the logger's `silent` and `--json` handling come from the config being loaded
- `saveJsonConfig(config, filePath)` writes formatted JSON; `autd init` writes `INITIAL_CONFIG` (`beyondRange`, `rules`, `cooldown`, `debug`, `silent`), never the deprecated fields
- Schema: `AlwaysUpToDateConfig` (see `src/types.ts`); `ConfigFile` is any subset of it plus `$schema`
- `beyondRange` and `rules` are validated strictly: an unknown level or rule throws instead of being ignored (ignoring `"react": "hodl"` would update a package meant to be held). `beyondRange` stays `undefined` when absent so the deprecated fields can still decide
- Every load failure (malformed JSON, invalid value) is a `ConfigError`. `openProject` throws it inside the command's `try`, so `reportFailure` prints it as one `❌` line with exit 1 (or the `--json` error object). Importing the CLI, `--help`, `--version` and `init` never load the config
- `cooldown` accepts: number (days), duration string (`'1 week'`, `'24h'`), or per-update-type object `{ patch, minor, major }` whose values are themselves numbers or duration strings. Anything `readDuration` cannot read (`"30 dyas"`, `-3`, `""`, `null`) and any other per-type key (`mnior`) is a `ConfigError` naming the key and the value (#217): a typo must not turn a supply-chain gate off
- `debug`, `silent`, `depsDev` and the deprecated `allowMinorUpdates` / `allowMajorUpdates` take `true` or `false` only (`"false"` and `1` are errors, not coerced). A top level that is not a JSON object (an array, `null`, a string) is a `ConfigError`. An unknown top-level key is a warning naming it and the known key within two edits of it, case ignored (`beyondrange` → `beyondRange`); `$schema` and the deprecated keys are known. `schema/config.schema.json`'s duration patterns accept the same strings as `readDuration` (a test compares them)

### Update Policy (`updateChecker.ts`)

`updateChecker(info, policy)` is pure: it returns a `Reason` always, with a `target` when the package moves (`within-range`, `past-range`, `rule-latest`) and without one when it is held. `filterPackages` builds the policy per run with `policyFromConfig(config)`.

1. Invalid semver: held (`invalid version …`)
2. Rule `hold`: held. Rule `latest`: target `latest`, any step size
3. Default: stay within the manifest range. Target is `wanted` (the highest version the range allows) when it is ahead of `current`; an exact pin has `wanted == current`, so it is held (`patch beyond the range`, etc.)
4. `beyondRange` (`none` | `patch` | `minor` | `major`) lets a package move past its range to `latest` when the step `current → latest` is at most that size. It applies to exact pins too. Rule `followRange` opts a package out

- `policyFromConfig()`: `beyondRange` if set, else the deprecated `allowMajorUpdates` → `major` / `allowMinorUpdates` → `minor` / `none`. `ruleFor(name)`: exact key in `rules`, then the longest matching `*` glob, then the deprecated lists (`updateAllowlist` → `latest`, `updateDenylist` → `hold`). `*` is the only wildcard
- `stepLevel()` folds pre-release diffs into patch/minor/major

### Cooldown (`cooldown.ts` + `duration.ts`)

- `cooldown.ts` is gate logic: normalize the user's config to `{ patch, minor, major }` days, decide if a release is too fresh given its update type and timestamp
- `duration.ts` is the generic time/format layer: `readDuration` accepts numbers, bare numeric strings (`7`, not `-3`, `1e3`, `0x10` or `.5`), and `<n><unit>` (s/min/h/d/w/mo/y, any case) and returns undefined for the rest; the config loader uses it to reject a bad `cooldown`. `parseDuration` is `readDuration` with 0 for undefined, so callers can fail open: `cooldown.ts` uses it, on a config the loader already validated
- `evaluateCooldown` returns `{ gated, ageDays, requiredDays }` — gating is a soft signal, callers decide what to do
- Cooldown gating judges the chosen `target` version, not `latest`, and only runs for packages with a target, so held packages never trigger network calls. It reads the release dates and deprecations of the name discovery looked up (`declared`): an `npm:` alias's target, never the package its manifest key names (#152)
- A target the gate holds falls back to the newest version between `current` and the target that is past cooldown for its own step and not deprecated (`lookup`, when the registry has it), a pre-release only when the target is one (#147). The row moves there with reason `cooldown: <target> released …`, which the report shows as `<target> held by cooldown (released …, needs Nd)`; it is held only when there is none. Below `wanted`, the fallback must also satisfy the range the manifest declares (the `declared` option, which the pipeline reads with `declaredDependency()` in `dependencySpecs.ts`): `applyPinned` puts that range back, and a range with a gap such as `^1 || ^3` doesn't cover every version below `wanted` (#151). With no range known, nothing below `wanted` qualifies

### Registry / .npmrc (`npmrc.ts`, `npmrcLoader.ts`, `registryRequest.ts`, `registryClient.ts`, `registry.ts`)

- `parseNpmrc(text, env, substitute?)` is ini 7's decode (quoting, `;`/`#` cuts, `key[]` arrays, parsing stops at the first `[section]`, `__proto__` skipped) plus a `Substitute` on keys and values, npm's by default (an unset `${VAR}` stays literal, `${VAR?}` is empty, `\${VAR}` is escaped); null leaves them as written
- A manager's `.npmrc` view is a list of `NpmrcLayer`s, highest first (`{ kind: 'env' | 'file', values }`), which `mergeNpmrcLayers` merges per key: the first layer that sets a key wins, whatever its type, and `view.origin(key)` names that layer. `envLayer(env, rule)` reads variables by an `EnvRule` (`prefix`, `key(rest, name)` where undefined skips the variable, `substitute`; empty values skipped); `npmrcFileLayer(file, env, { substitute, omitReferences })` reads a file; `substitute: null` expands nothing, and `omitReferences` leaves out an entry whose key or value still holds `${…}`, so a lower layer decides. An `EnvRule`'s optional `rank(name, key)` picks among variables naming the same key (higher wins, later in `env` among equals). `managerRegistryConfig(adapter, dir, sources)` is the session's wiring: the merge of the adapter's layers, `registryConfigFrom`, then the `registryConfig?` hook. `NpmrcSources` (env, home, execPath, platform) is injectable for tests; a layer never throws, an unreadable file is empty
- `npmNpmrcLayers(cwd, sources)` is npm's list: `npm_config_*` env (any case, `_` → `-`), project, user (`~/.npmrc`), global (`<prefix>/etc/npmrc`), builtin. The project file is the `.npmrc` of the npm project root: from a workspace member, the root's. `loadNpmrc` is its merge
- `registryConfigFrom(npmrc, cwd, sources)` builds `RegistryConfig` (registry, `scopedRegistries`, `credentials` by `//host[:port]/path/` prefix, `ca`, `strictSSL`, `proxy`, `fetchRetries`, `fetchTimeout`, `maxSockets`). Unscoped `_authToken` and `always-auth` are ignored, as npm 9+ does; yarn v1 reads both (`yarnV1Auth`, in the yarn v1 `.npmrc` notes below)
- An unusable registry value (a URL that does not parse, a non-http(s) one, one holding `${…}` or, in its host, a `$`, an empty one; npm 11.19.1 fails on `https://${UNSET}/` with ENOTFOUND) is not skipped where the manager fails on it. `registryConfigFrom(view, cwd, sources, empty?)` (the `NpmrcView`, so each value is named by its layer; a layer's optional `labels` give the key as the source spells it: the variable, `registries."@acme"`) leaves it out of `registry` / `scopedRegistries` and records it in `RegistryConfig.unusable` (`registry`, `scopes`: `{ key, value, source, reason }`, the value shown by `describeUnusable`: `<scheme>://<host>/` with a path behind `pathMarker`, userinfo and query never shown; a value with no scheme and host is `(value not shown)` unless it is only `${NAME}` references). `unusableRouteFor(name, config)` gives the one a package is routed through (its scope's, else the default's, unless a usable scope route covers it); the session itself refuses such a package (`releaseTimes` returns `{}` with a debug line and sends nothing; `lookup` answers `invalid`), and `discoverFromRegistry` asks `session.unusableRoute(name)` first and throws a `discover` `StepError` (`<pm> can't use <key> \`<value>\` from <file>; fix or remove it`) instead of asking another registry. Only the winning value counts: a bad value a higher layer shadows is not an error. Verified 2026-10-27 (npm 11.19.1, pnpm 12.15.0, yarn 1.22.22, bun 1.4.4, each with `install`): all four fail on an unparseable URL, text, `ftp://…`and an unset`${VAR}`as the default or a scope route (a scope route only when a package of that scope is resolved), in`.npmrc`, the environment and the manager's own file (bunfig.toml, pnpm yaml, `.yarnrc`). The exception is pnpm, which skips a `${…}` in a project file (`.npmrc`, `pnpm-workspace.yaml`) and falls through, as autd does; a `${VAR}`that pnpm's global files expand to nothing is an empty value, which pnpm fails on. Empty values differ and are the adapter's`emptyRegistry`: npm fails on an empty default and skips an empty scope, pnpm fails on both, yarn and bun skip both. Not mirrored: yarn also fails the whole run on an unset `${VAR}`in a shadowed`.npmrc` registry line
- `session.releaseTimes(name, window?)` (from `createRegistrySession(cwd)`) refuses an unusable route (`{}`, nothing sent) and otherwise calls the reader's `releaseTimes`, which never rejects. It looks the name up with the reader's memoized `lookup` (a failed lookup is `{}`, no request), takes that lookup's `publishedAt` as the times, and asks for the full packument (the abbreviated one has no `time`) only when `window` judges a version still without one: the versions above `window.current`, up to and including `window.target` (every untimed version with no window, or when either end is not semver, e.g. a `missing` row). The request is `get` + `revalidate` on the package's registry, so it takes the host's limiter slot, and the answer is memoized per name per run (the untimed versions are the same on every call). Its times win over the lookup's, only for versions both the document and the lookup list (a `time` entry of an unpublished version, `created` and `modified` are dropped, and so is a version a stored document still lists after an unpublish), and a failed or unreadable document, or any throw while reading it, keeps the lookup's times with a debug line; the cooldown gate holds a target with no known time (#139). The debug line, logged after the response and naming the judged versions that caused the request, tells them apart (#176): `Reading the full packument of <name> for publish times: …` when a body came back, `Revalidated the full packument of <name> for publish times (304): …` when none did. A failed request has its own line, and a cache answer logs none: a stored document past its TTL that the coverage rule answers counts as `covered` in the run summary
- The client sends credentials only to the longest `.npmrc` prefix that matches the request URL, and recomputes them on each redirect (yarn v1 and berry have their own rules, below). Retries cover 408, 420, 429, 5xx, ECONNRESET, ECONNREFUSED and ETIMEDOUT with a short capped backoff; a `Retry-After` over 1 s stops retrying
- `registry.ts` imports `registryClient` with `await import()` on the first request, so the client loads with the first request, not when a command starts; keep top-level imports there to types, `registryRequest`, `npmrcLoader` and `logger`
- `openProject` makes one `RegistrySession` per run (`Project.registry`), its `.npmrc` view loaded at the project root, where every manager command runs, whatever the cwd (#127): `registryConfig()` reads the `.npmrc` layers and `cafile` on its first call, `client()` creates the one client, so every registry request in the run shares both. A session reads and loads nothing until asked; `close()` warns once when a host throttled the run (`throttledNotice`, #174), destroys the agents (safe twice, or before any request), and commands call it in a `finally`. `loadConfig`, `clientOptions` and `endpoints` are test seams; `depsDev` is the config switch
- `getJson(url, registry, { signal, accept, timeout, retries })`: `accept` defaults to `application/json`, `timeout` to `fetch-timeout` (ms), `retries` to `fetch-retries`; all hold across redirects and retries. The reader sends deps.dev requests with `retries: 0`. `stats()` returns copies and counts per `url.host`: `responses` (every status), `throttled` (the 429s among them, a retried request's each), `bodyBytes` (2xx bodies as received) and `decodedBytes` (after gunzip)
- `session.lookup(name)` (`registryReader.ts`, loaded with `await import()` on the first call) returns a `PackageLookup` and never rejects for a network, HTTP or parse failure:
  - An invalid name (`isValidPackageName`) is `invalid` with no request. A public npm name (registry root is `https://registry.npmjs.org/` or `https://registry.yarnpkg.com/`) fetches `/-/package/<name>/dist-tags` and deps.dev together. When deps.dev lists `latest` the result is `source: 'deps.dev'`; otherwise (deps.dev 404, 429, 5xx, unreachable, unreadable, or `latest` missing) the abbreviated packument is read, and every version it lists that deps.dev also lists gets deps.dev's `publishedAt` (`withTimes`; `source` stays `'packument'`, and the version list and deprecations stay the packument's), so only the newest versions deps.dev has not indexed lack a time. A dist-tags 404 is `not-found`; any other dist-tags failure takes the packument path, a 429 included: the results stay correct, and the run says so at `close()` (#174)
  - Any other registry, a scope's registry, or `depsDev: false` takes one GET with `ABBREVIATED_ACCEPT`, retried once with `application/json` on a 404 (as pacote does). The packument's own `latest` is used when it lacks the dist-tags' one, else the highest stable version
  - deps.dev gets only its own URL as the client's registry base, so no `.npmrc` credentials go to it. A 429 or a timeout turns deps.dev off for the rest of the run (one debug line). Any other 5xx or transport failure falls back to the packument for that package only, and the third such failure in a run turns deps.dev off; a 404 does not count. The decision is made inside the failed request's limiter slot, before the next queued request starts. deps.dev requests time out at `min(fetch-timeout, 5 s)` with no retries (the 5 s is the reader's `depsDevTimeout` option, which tests lower), and a request still queued when the breaker trips is skipped once it reaches the front
  - Requests go through one limiter per host (`new URL(url).host`), each of `maxsockets`, the client's per-host agent cap: a queued request never waits in an agent queue and burns its timeout, and only that many packument bodies per host are buffered at once. With two hosts (dist-tags and deps.dev), up to `2 × maxsockets` requests are in flight; measured 2026-10-26 on the 40-package benchmark, lookups took 0.57–0.70 s against 0.75 s with one run-wide limiter
  - A body the client cannot parse as JSON is a `request` failure; a JSON body that is not a packument is `invalid`. `not-found` and `invalid` reasons name the registry's host; a `request` reason is the client's message, which carries the URL as `describeUrl(url, registry)` shows it: the origin, then `/…[3fa9c1]` for the registry's own path (a token can sit there, as in Gemfury's `https://npm-proxy.fury.io/<TOKEN>/<user>/`), then the rest: `https://npm-proxy.fury.io/…[3fa9c1]/left-pad`. The marker is the first 6 hex characters of the SHA-256 of the registry path (`pathMarker`), so one registry always shows the same marker and two registries on one host differ. The public npm registries and deps.dev, and a registry at the origin root, show whole. A redirect target (`{ redirect: true }`: every hop after the first, and the target of a refused redirect) and any URL outside the registry path show the origin and `/…`. Never userinfo or query; an unparseable URL gives `(invalid URL)`, `describeUrl` never throws. The client words every failure through its one `requestError`, so no site formats a raw URL. ### Manifest Specs (`files.ts`)

- Every writer builds the new spec with `nextVersionSpec()`: a single comparator (`^1.2.3`, `~1.2.3`, `1.2.3`) keeps its decorator, so an exact pin stays exact; an `npm:` alias keeps the alias and rewrites the spec inside it; a spec that can't keep its shape (`1.x`, `*`, `>=1 <2`, `^1 || ^2`) is written in the project's save style; git, file and URL specs are left alone
- Each adapter's `saveStyle(cwd)` reads that style where its manager's current version keeps it: npm `.npmrc` `save-exact` / `save-prefix`; pnpm `pnpm-workspace.yaml` `saveExact` / `savePrefix` (not `.npmrc`); yarn berry `.yarnrc.yml` `defaultSemverRangePrefix` (`''` = exact); bun `bunfig.toml` `[install] exact` or `.npmrc` `save-exact` (no prefix setting). Default `^`. Managers read it only when they write a beyond-range spec
- `catalog:` and `workspace:` references are never rewritten, and neither is a `peerDependencies` range: `updatePackageJson` writes `dependencies`, `optionalDependencies` and `devDependencies` only, as the managers' own update commands do (#155)
- JSON manifests are written back in their own format (`formatLike`): the detected indentation (tabs or N spaces), CRLF or LF, and a final newline only if the file had one, so a bump changes one line
- `updatePNPMWorkspaceYAML(cwd, versions, style, catalog?)` rewrites only entries under `catalog:` and under each named catalog in `catalogs:`; every other block (`overrides`, `peerDependencyRules`, settings) stays byte-for-byte. With `catalog` (`default` for `catalog:`) only that catalog moves, so `catalog:react18` never rewrites `react19`'s entry; the adapters call it once per catalog from `splitCatalogUpdates()`, which returns `catalogs` (catalog → name → version). An entry's value is read whole (`>=18.0.0 <19`, `"^17 || ^18"`, up to a trailing ` #` comment) and replaced whole; it keeps its quotes and its comment
- Bun reads `workspaces.catalog` / `workspaces.catalogs` as well as the top-level fields; when the `workspaces` one is set it replaces the top-level one as a whole, per field (verified on bun 1.4.4). `readBunCatalogs` and `updateBunCatalogs(cwd, versions, style, catalog?)` follow that
- `buildUpdateDescriptors()` applies the same rule to produce `name@spec` for managers that write the manifest themselves (yarn), reading `dependencies`, then `devDependencies`, then `optionalDependencies`

### Report (`report.ts`, `logger.report`)

`outcomeOf(result)` files an `UpdateResult` under `update` when it moved, else by `reason.code` through `SECTION_OF: Record<ReasonCode, Outcome | undefined>` (exhaustive, so `tsc` fails on a code with no section; `not-targeted` maps to `undefined` and is left out). No prefix matching on `reason.message`. `groupResults` merges rows that share name, versions and note across manifests, sorts by name then root first, and orders sections update → left in place → cooldown → past the range → rule → override → peer → deprecated → license → engines → held with → other. A moving row's note is empty within its range (the default), `rewrites its range` past it in the plan and `range rewritten` once applied (`groupResults(results, phase)`), with the notes joined by `NOTE_SEPARATOR` (a `·` with a space either side). A hold that cleared a target keeps it as `UpdateResult.judged` (cooldown, peer, target peers, deprecation, license, engines, held with, override, not applied; set by `heldFor`, the cooldown hold, `holdTogether`, the override hold and `checkApplied`), and the report shows `target ?? judged ?? latest`, colored by the step from `current` to that version, so the version, its age and its note describe the same release (#221); `judged` is not in `--json`, whose `updateType` is unchanged. A held row past its range shows its step (`major`), and the section's `hint` names the `beyondRange` level once (`rangeHint`: `"minor" would move 1, "major" all 3` when the steps differ). `ReportRow.level` is the row's `updateType`; `formatRow` colors `to` from `splitAtChange(current, to)` (red major, yellow minor, green patch or unknown) and leaves `current` plain. `logger.report`'s `next` (from `check` and `--dry-run`: `autd update`, plus the targeted names) prints `Run <next> to apply.` when something would move (`in the workspace root` from a member), and `elapsedMs` (applied `update`, from `pipeline.update`) ends the summary line with `(took 12.3s)` (`formatElapsed`). A moving row with code `engines-fallback` (npm's walk-back, #200) stays under update, and its note adds the stripped message (`5.1.6 needs node >=14.17 (running node 12.22.12)`); `cooldown-fallback` adds `<version> held by cooldown (released …, needs Nd)`. A new reason needs a code in `reasons.ts` and a section in `SECTION_OF`.

`UpdateResult.reason` is a required `Reason { code, message }`; `warnings?: Reason[]` replaces a single warning (a `latest` rule moving past a peer conflict, deprecation, license change or engines hold). `jsonDocument.ts` maps a row to the `--json` shape (`rowOf`): `outcome` is `update` when `updated`, `not-applied` / `not-targeted` by code, else `held`; `current: 'missing'` becomes `null`, `workspace` defaults to `"."`, `target` and `releaseAge` become `null` when absent.

A member run (#123) passes `{ member }` (the member's path): there is one manifest, so the manifest column is left out whatever the rows hold, and `logger.memberRun(manager, path, count)` has printed `<pm> workspace member <path> (1 of N manifests)` first.

### Package Filtering (`filterPackages.ts`)

- Async. Signature: `filterPackages(outdated, { config, registry, targetPackages?, cwd?, now?, overrides?, declared? })`; `registry` is `Pick<RegistrySession, 'releaseTimes'>`, the project's session, and is asked `releaseTimes(name, { current, target })` for the row being judged; `config` is the project's loaded config, never loaded inside
- Runs `updateChecker` on every outdated package with the policy for `cwd`
- When cooldown is enabled (`cooldown > 0` for any update type), asks the registry for release times for packages with a target and applies the gate; a row whose step has a zero-day cooldown (`cooldownDaysFor`, e.g. `{ patch: 0, minor: 7 }`) is not asked about and keeps no `releaseAge`
- Returns `UpdateResult[]` with name, current, wanted, latest, `target` (when updated), updateType (`current → target`, else `current → latest`), updated, `reason` (`{ code, message }`), optional `warnings` and `releaseAge`
- With `overrides` (the pipeline passes `adapter.overrides(cwd)`), a target outside the range of an override the manager enforces is held (`controlled by <field> (<range>)`), whatever the rules say; a held package names the override when `latest` is outside it too. Fields, as the current manager versions read them (verified by real installs): npm `overrides`; yarn berry `resolutions` (yarn v1 does not apply them to a direct dependency, so nothing is held); pnpm `overrides` in pnpm-workspace.yaml (pnpm 12 ignores `pnpm.overrides` / `resolutions` in package.json); bun `overrides` and `resolutions`. `$name` references and keys that only reach another package's dependencies (`a>b`, `a/b`, objects without `.`) don't pin
- Peer pass (`holdPeerConflicts`), when anything has a target: a target an installed package's peer range excludes is held (`peer conflict: <pkg>@<ver> needs <name> <range>`). Ranges from packages also moving in the run don't count here: their new peers are the target-peer pass's (below). Repeats until stable, since a hold can expose another conflict. A `latest` rule still moves, with `warning` set. Runs before cooldown, so held packages cost no network. ~22 ms for ~600 installed packages
- Deprecation pass (`holdDeprecated`, #195), after the cooldown and before the last `settle`, so it judges the final target (a cooldown fallback is never deprecated): a moving row whose target the session's lookup marks deprecated is held as `deprecated: <message>` (the message on one line, control characters dropped; `no message given` without one). A `latest` rule moves it, and so does an installed version deprecated with the same message (every next 14.0.x is; an installed version with another message, or none, is held); either way the message is `warning`. It reads `registry.lookedUp` (the session's own lookups: discovery's, so no request) by the name discovery looked up (`declared`, an alias's target). Warnings from several passes are joined with `; `, each once (`withWarning`)
- Manifest step (#196), in `signals` right after the deprecation pass settles: `readTargetManifests` reads each still-moving row's target manifest (`registry.versionManifest`, by `lookupName`), so held rows cost no request, then a per-plan `passes` array of synchronous `ManifestPass(rows, { manifests, lookupName, policy })` functions runs in order (built in `signals`; today the engines pass, which holds or warns and never moves a row; an `undefined` manifest is a state each pass decides), then `settle` with the target peers. Order: peers, cooldown, deprecation, manifests, engines walk-back (npm), license, passes (engines), settle with target peers
- Engines walk-back (`fitRunningNode` in `nodeFit.ts`, #200), in `signals` right after `readTargetManifests` and before the license pass, only when `FilterPackagesOptions.skipsEnginesExcluded` is set (the pipeline passes `adapter.skipsEnginesExcluded?.(root)`: npm only). npm installs the highest in-range version whose `engines.node` fits its Node (npm-pick-manifest's `engineOk`; `npmAcceptsNode`, which fails an invalid range where #199's `enginesHold` lets it through; probed on npm 12.2.2 and 11.19.1, 2026-11-08; pnpm and bun install the highest version whatever the engines, yarn not verified). A moving row with `target === wanted` whose target manifest is known and is not accepted by `node` (the running Node; npm has no `nodeVersion` hook) or excluded by the project's declared `engines.node` (#233: the owning manifest's, as the engines pass reads it, `enginesHold` with no running Node, so the same `semver.subset` rule) is walked, though npm itself would install a target the declared range alone excludes, since #199 would hold it anyway: candidates come from `registry.lookedUp` (no request; already release-age gated), satisfy the range the manifest declares (`declared`), are above `current` and below the target and not deprecated, newest first, at most `ENGINES_WALK_LIMIT` (5) per (name, target, range, declared, current), each read with `versionManifest` (cached forever per version). The first whose `engines.node` fits npm's Node and the declared range (when one is declared) and that the cooldown allows (`cooldownOf`, only when the step's cooldown is on, with the window the cooldown pass used) becomes the target, with `updateType` re-derived, `releaseAge` the fit's, reason `engines: <target> needs node <range> (running node <v>)`, or `(the project declares <range>)` when the declared range excludes the target, and its manifest added to the map the later passes (license, #199's engines, target peers) read. An unknown candidate manifest stops the walk and keeps the target (a debug line), as does reaching the cap or finding nothing that fits both: #199 then holds the target. Past-the-range targets and cooldown fallbacks are not walked, and a `latest` rule does not stop it. Nothing is read when no target fails, so a warm cache sends none (`findOutdated` plans nothing; `check` and `check --json` do). The row has `target < wanted`, so `splitUpdates` pins it (`beyondRange: false`) and `checkApplied` wants exactly that version. Known differences from npm-pick-manifest, all rare: a fitting untagged version above an excluded `latest` tag (npm picks it, autd walks down and pins lower); a deprecated fitting version beats a non-deprecated excluded one in npm's sort (autd keeps the target, #199 holds it); `engines.npm` is not modeled; npm's `loose` satisfies against `wantedVersion`'s strict one. Accepted: once pinned and installed, the next run sees `wanted` 5.1.6 and no candidate above `current`, so #199 holds it with `engines: needs node …` where `npm outdated` lists nothing
- License pass (`holdLicenseChanges`, #197), in `signals` after the engines walk-back and before the `passes`; it is called there directly, not through them, because it is async (it may read the current version's manifest), and `passes` holds the synchronous ones: a moving row whose target's license differs (`sameLicense`) from the installed version's is held as `license change: <current> → <target>` (each side cut to 40 characters; `none` when a side declares nothing). A `latest` rule moves it with that text as `warning`. The installed license comes from `readInstalledManifests` (`installed.ts`, sharing `scanInstalled` with `readInstalledPackages`: the member's nested copy first, then the root's, only a copy at the row's `current`), else `registry.versionManifest(lookupName, current)` once per pair (npm lockfile-only, berry PnP, a mismatched copy). Only rows whose target manifest is known are checked; a row whose target or current manifest is unknown moves, and the plan logs one `logger.warn`, `No version manifest for target <list>; installed <list>: they move without license, peer or engines checks` (name@version, each list the first 10, then "and N more"; targets and installed versions apart, as their fixes differ)
- Engines pass (`enginesPass`, #199), the one entry of `passes`, after the license pass and before the target-peer settle (a peer held for engines counts as not moving for #198): a moving row whose target manifest's `engines.node` (`enginesNode`) excludes the project's Node is held as `engines: needs node <target> (the project declares <range>)`. The declared range is the owning manifest's `engines.node` (a member's own, else the root's; `declaredNodeRange` keeps only a real constraint, `*`, `x` and `>=0` declare nothing, and an invalid value logs a debug line naming the file), and every Node it allows must fit the target (`semver.subset` with `includePrerelease`). With nothing declared the running Node is judged (`semver.satisfies`, `includePrerelease`): `(running node <v>)`, or `(pnpm nodeVersion <v>)` when the adapter's `nodeVersion(cwd)` answers (`FilterPackagesOptions.node` / `nodeLabel`, passed by `plan`). Under a Bun runtime (`runningNode()` null) with nothing declared the row is skipped, with one debug line. A target with no `engines.node`, or `*` / `>=0`, moves; an unknown manifest moves and joins the plan's unknown-manifest warning. A `latest` rule moves it with the text as `warning`. Probed 2026-11-07: npm 11.19.1 judges engines by the running Node only, pnpm 12.18.0 by `nodeVersion` when set else the running Node, bun 1.4.4 ignores engines; none judges by the project's own `engines.node`, so the declared-range hold is autd's own signal. Limitation: a target of touching pieces (`^22.12.0 || >=23`) against a declared `>=22.12.0` is held though it covers it, since `semver.subset` does not join adjacent ranges
- Target-peer pass (`targetPeerConflict`, #198), inside the last `settle(rows, targetPeers)` of `signals` (after `holdPeerConflicts`, before `holdTogether`), only when the manifests map is non-empty: for each moving row's target manifest, each `[peer, range]` (own name skipped; a range `semver.validRange` rejects, e.g. `workspace:*`, skipped with a debug line) is checked, with `includePrerelease`, against the version the plan leaves that peer at: its row in the same manifest (target if moving, else current unless `missing`), else the root's row from a member, else the installed version (`FilterPackagesOptions.installed`, called once per plan; default `readInstalledVersions(cwd, rows, { declaredOnly: false })`; the pipeline passes the lockfile reader when `adapter.installedFromLockfile` answers). A peer found nowhere is fine: optional (`optionalPeers`), or left to the manager with a debug line. A miss holds the row as `peer conflict: <name>@<target> needs <peer> <range> (installed <v>)` or `(moving to <v>)`, in the existing `peer` report outcome. A `latest` rule moves, and the warning is added once the plan is stable. Matches npm, stricter than pnpm and bun (probed 2026-11-08)
- A workspace record expands to one `UpdateResult` per (package, manifest) (`expandWorkspaces`), each with `workspace`; single-package results have no `workspace` key. `holdTogether` holds a package's moving rows whenever another row of it is held while its range allows newer (`held with <path> (<reason>)`), because the in-range commands are workspace-wide; an exact pin blocks nothing. The peer pass and `holdTogether` repeat until nothing changes (`settle`), once before the cooldown and again after it, so a row held by either, or by the cooldown, stops counting as moving for the peer check. yarn v1 moves a member's packages with root installs (`pinMembers`, #127), so it holds the same way
- `splitUpdates(results)` also returns `manifests` (`ManifestPlan[]`, root first, then by path) and divides the chosen updates into `withinRange` names (target == wanted: hand to the manager, write nothing) and `beyondRange` name → version (write the manifest spec first). A row whose target is neither `wanted` nor `latest` (a cooldown fallback) is `pinned` (`PinnedRow[]`), and so is every other moving row of its package; with `{ pinMembers: true }` (the adapter's `pinMembers`, yarn v1, #127) so is every moving row of a package that moves in a member; `names` and `manifests` leave pinned rows out, and `src/managers/pin.ts` applies them first
- Used by the pipeline's `plan` (update, dry-run, and interactive mode)
