# The plan (`filterPackages` and its passes)

## Overview

The plan turns discovery's outdated packages into `UpdateResult[]`: the policy picks a target, then a fixed order of passes holds, walks back or warns, each judging the version the previous pass left. `src/utils/filterPackages.ts` drives it and sits one directory up, so this file loads only when you touch `plan/`: read it before changing `filterPackages.ts` too.

## Architecture

- Async. Signature: `filterPackages(outdated, { config, registry, targetPackages?, cwd?, now?, overrides?, declared? })`; `registry` is the project's session (`PlanRegistry`: `Pick<RegistrySession, 'releaseTimes'>` plus optional `lookup`, `lookedUp` and `versionManifest`), and is asked `releaseTimes(name, { current, target })` for the row being judged; `config` is the project's loaded config, never loaded inside
- Runs `updateChecker` on every outdated package with the policy for `cwd`, then the passes. Order: overrides and policy, peers, cooldown, deprecation, manifests, engines walk-back (npm), license, passes (engines), settle with target peers
- Returns `UpdateResult[]` with name, current, wanted, latest, `target` (when updated), updateType (`current → target`, else `current → latest`), updated, `reason` (`{ code, message }`), optional `warnings` and `releaseAge`
- Used by the pipeline's `plan` (update, dry-run, and interactive mode)
- A hold beats the config: overrides and a manager's release-age gate (applied to every lookup before the plan sees it, `src/utils/REGISTRY.md`) beat everything, then the passes below. A `latest` rule moves a row past a peer conflict, deprecation, license change or engines hold, with the reason as an `UpdateResult.warnings` entry. Warnings from several passes are joined with `; `, each once (`withWarning`)

## Update policy (`../updateChecker.ts`)

`updateChecker(info, policy)` is pure: it returns a `Reason` always, with a `target` when the package moves (`within-range`, `past-range`, `rule-latest`) and without one when it is held. `filterPackages` builds the policy per run with `policyFromConfig(config)`.

1. Invalid semver: held (`invalid version …`)
2. Rule `hold`: held. Rule `latest`: target `latest`, any step size
3. Default: stay within the manifest range. Target is `wanted` (the highest version the range allows) when it is ahead of `current`; an exact pin has `wanted == current`, so it is held (`patch beyond the range`, etc.)
4. `beyondRange` lets a package move past its range to `latest` when the step `current → latest` is at most that size. It applies to exact pins too. Rule `followRange` opts a package out

- `policyFromConfig()`: `beyondRange` if set, else the deprecated `allowMajorUpdates` → `major` / `allowMinorUpdates` → `minor` / `none`. `ruleFor(name)`: exact key in `rules`, then the longest matching `*` glob, then the deprecated lists (`updateAllowlist` → `latest`, `updateDenylist` → `hold`). `*` is the only wildcard
- `stepLevel()` folds pre-release diffs into patch/minor/major

## Cooldown and durations (`../cooldown.ts`, `../duration.ts`)

- `cooldown.ts` is gate logic: normalize the user's config to `{ patch, minor, major }` days, decide if a release is too fresh given its update type and timestamp. `evaluateCooldown` returns `{ gated, ageDays, requiredDays }`: gating is a soft signal, callers decide what to do. The gate and its fallback are the cooldown pass below
- `duration.ts` is the generic time/format layer: `readDuration` accepts numbers, bare numeric strings (`7`, not `-3`, `1e3`, `0x10` or `.5`), and `<n><unit>` (s/min/h/d/w/mo/y, any case) and returns undefined for the rest; the config loader uses it to reject a bad `cooldown`. `parseDuration` is `readDuration` with 0 for undefined, so callers can fail open: `cooldown.ts` uses it, on a config the loader already validated

## The passes

- **Overrides**: with `overrides` (the pipeline passes `adapter.overrides(cwd)`), a target outside the range of an override the manager enforces is held (`controlled by <field> (<range>)`), whatever the rules say; a held package names the override when `latest` is outside it too. Fields, as the current manager versions read them (verified by real installs): npm `overrides`; yarn berry `resolutions` (yarn v1 does not apply them to a direct dependency, so nothing is held); pnpm `overrides` in pnpm-workspace.yaml (pnpm 12 ignores `pnpm.overrides` / `resolutions` in package.json); bun `overrides` and `resolutions`. `$name` references and keys that only reach another package's dependencies (`a>b`, `a/b`, objects without `.`) don't pin
- **Peer pass** (`holdPeerConflicts`), when anything has a target: a target an installed package's peer range excludes is held (`peer conflict: <pkg>@<ver> needs <name> <range>`). Ranges from packages also moving in the run don't count here: their new peers are the target-peer pass's. Nor do ranges from an installed package the run replaces: with the install's graph (`FilterPackagesOptions.installedGraph`, default `readInstalledGraph(cwd)`, `src/utils/installedGraph.ts`: pnpm's `node_modules/.pnpm/lock.yaml`, read with the peers; other managers have none yet, so every range counts there), `keptInstalls` walks from each workspace's direct dependencies the run doesn't move, through what each depends on; a range counts only from a package it reaches (or one the graph doesn't list). A moving row's installed version is replaced, so what it depended on is kept only when its target's `dependencies`, `optionalDependencies` or `peerDependencies` still admit that version (a range `semver` can't read keeps it); a peer edge to a package the run moves keeps nothing (the peer resolves to the moved version); a workspace dependency with no row (pnpm's auto-installed peers of a member, under the same catalog) moves with a moving row of its name at that version. Before the targets' manifests are read, a moving row keeps nothing, so such a hold waits for the last `settle`, which always gets `targetPeers` (manifests or not) and asks each target; with no manifest for a target, everything it depended on is kept, as before. This is what moves tiptap: every tiptap 3 package pins its peers exactly (`@tiptap/extension-blockquote@3.33.0` needs `@tiptap/core 3.33.0`) and `@tiptap/starter-kit` and `@tiptap/react` pin the extensions, so the old extensions held `core` and `pm` forever, and an update moved only the packages without peers, leaving two copies of `core` installed (the regression tests replay real pnpm 12.18.0 installs of both states). Not modeled: a package the run replaces is not asked whether its own new version still depends on what it had (that needs its manifest), so it keeps nothing. Repeats until stable, since a hold can expose another conflict. Runs before cooldown, so held packages cost no network. ~22 ms for ~600 installed packages. The ranges come from `FilterPackagesOptions.installedPeers` when given, else `readInstalledPeers(cwd)` (`src/utils/peers.ts`); the pipeline passes the lockfile's `LockedInstall.peers` when `adapter.installedFromLockfile` answers with one (#232: npm with only `package-lock.json`, `readLockedPeers`; berry under PnP, `readBerryLockPeers`), so node_modules decides wherever it exists
- **Cooldown** (`holdCooldown`), when cooldown is enabled (`cooldown > 0` for any update type): asks the registry for release times for packages with a target and applies the gate (`evaluateCooldown`, `src/utils/cooldown.ts`); a row whose step has a zero-day cooldown (`cooldownDaysFor`, e.g. `{ patch: 0, minor: 7 }`) is not asked about and keeps no `releaseAge`. It judges the chosen `target` version, not `latest`, and only runs for packages with a target, so held packages never trigger network calls. It reads the release dates and deprecations of the name discovery looked up (`declared`): an `npm:` alias's target, never the package its manifest key names (#152). A target with no known publish time is held (`cooldown: release date unknown, requires Nd`, #139)
  - A target the gate holds falls back to the newest version between `current` and the target that is past cooldown for its own step and not deprecated (`lookup`, when the registry has it), a pre-release only when the target is one (#147). The row moves there with reason `cooldown: <target> released …`, which the report shows as `<target> held by cooldown (released …, needs Nd)`; it is held only when there is none. Below `wanted`, the fallback must also satisfy the range the manifest declares (the `declared` option, which the pipeline reads with `declaredDependency()` in `dependencySpecs.ts`): `applyPinned` puts that range back, and a range with a gap such as `^1 || ^3` doesn't cover every version below `wanted` (#151). With no range known, nothing below `wanted` qualifies. The fallback is pinned through apply by `src/managers/pin.ts`
- **Deprecation** (`holdDeprecated`, #195), after the cooldown and before the last `settle`, so it judges the final target (a cooldown fallback is never deprecated): a moving row whose target the session's lookup marks deprecated is held as `deprecated: <message>` (the message on one line, control characters dropped; `no message given` without one). A `latest` rule moves it, and so does an installed version deprecated with the same message (every next 14.0.x is; an installed version with another message, or none, is held); either way the message is `warning`. It reads `registry.lookedUp` (the session's own lookups: discovery's, so no request) by the name discovery looked up (`declared`, an alias's target)
- **Manifest step** (#196), in `signals` right after the deprecation pass settles: `readTargetManifests` reads each still-moving row's target manifest (`registry.versionManifest`, by `lookupName`), so held rows cost no request, then a per-plan `passes` array of synchronous `ManifestPass(rows, { manifests, lookupName, policy })` functions runs in order (built in `signals`; today the engines pass, which holds or warns and never moves a row; an `undefined` manifest is a state each pass decides), then `settle` with the target peers
- **Engines walk-back** (`fitRunningNode`, #200), in `signals` right after `readTargetManifests` and before the license pass, only when `FilterPackagesOptions.skipsEnginesExcluded` is set (the pipeline passes `adapter.skipsEnginesExcluded?.(root)`: npm only). npm installs the highest in-range version whose `engines.node` fits its Node (npm-pick-manifest's `engineOk`; `npmAcceptsNode`, which fails an invalid range where #199's `enginesHold` lets it through; probed on npm 12.2.2 and 11.19.1, 2026-11-08; pnpm and bun install the highest version whatever the engines, yarn not verified). A moving row with `target === wanted` whose target manifest is known and is not accepted by `node` (the running Node; npm has no `nodeVersion` hook) or excluded by the project's declared `engines.node` (#233: the owning manifest's, as the engines pass reads it, `enginesHold` with no running Node, so the same `semver.subset` rule) is walked, though npm itself would install a target the declared range alone excludes, since #199 would hold it anyway. Candidates come from `registry.lookedUp` (no request; already release-age gated), satisfy the range the manifest declares (`declared`), are above `current` and below the target and not deprecated, newest first, at most `ENGINES_WALK_LIMIT` (5) per (name, target, range, declared, current), each read with `versionManifest` (cached forever per version). The first whose `engines.node` fits npm's Node and the declared range (when one is declared) and that the cooldown allows (`cooldownOf`, only when the step's cooldown is on, with the window the cooldown pass used) becomes the target, with `updateType` re-derived, `releaseAge` the fit's, reason `engines: <target> needs node <range> (running node <v>)` (code `engines-fallback`), or `(the project declares <range>)` when the declared range excludes the target, and its manifest added to the map the later passes (license, #199's engines, target peers) read. An unknown candidate manifest stops the walk and keeps the target (a debug line), as does reaching the cap or finding nothing that fits both: #199 then holds the target. Past-the-range targets and cooldown fallbacks are not walked, and a `latest` rule does not stop it. Nothing is read when no target fails, so a warm cache sends none (`findOutdated` plans nothing; `check` and `check --json` do). The row has `target < wanted`, so `splitUpdates` pins it (`beyondRange: false`) and `checkApplied` wants exactly that version
  - Known differences from npm-pick-manifest, all rare: a fitting untagged version above an excluded `latest` tag (npm picks it, autd walks down and pins lower); a deprecated fitting version beats a non-deprecated excluded one in npm's sort (autd keeps the target, #199 holds it); `engines.npm` is not modeled; npm's `loose` satisfies against `wantedVersion`'s strict one. Accepted: once pinned and installed, the next run sees `wanted` 5.1.6 and no candidate above `current`, so #199 holds it with `engines: needs node …` where `npm outdated` lists nothing
- **License** (`holdLicenseChanges`, #197), in `signals` after the engines walk-back and before the `passes`; it is called there directly, not through them, because it is async (it may read the current version's manifest), and `passes` holds the synchronous ones: a moving row whose target's license differs (`sameLicense`, `src/utils/license.ts`) from the installed version's is held as `license change: <current> → <target>` (each side cut to 40 characters; `none` when a side declares nothing). Case, whitespace, outer parentheses and operand order of a flat OR/AND, the file named by `SEE LICENSE IN` and GNU's deprecated ids are not a change; `MIT/X11` against `MIT` is, and so is `Apache 2.0`. A `latest` rule moves it with that text as `warning`. The installed license comes from `readInstalledManifests` (`installed.ts`, sharing `scanInstalled` with `readInstalledPackages`: the member's nested copy first, then the root's, only a copy at the row's `current`), else `registry.versionManifest(lookupName, current)` once per pair (npm lockfile-only, berry PnP, a mismatched copy). Only rows whose target manifest is known are checked; a row whose target or current manifest is unknown moves, and the plan logs one `logger.warn`, `No version manifest for target <list>; installed <list>: they move without license, peer or engines checks` (name@version, each list the first 10, then "and N more"; targets and installed versions apart, as their fixes differ)
- **Engines** (`enginesPass`, #199), the one entry of `passes`, after the license pass and before the target-peer settle (a peer held for engines counts as not moving for #198): a moving row whose target manifest's `engines.node` (`enginesNode`) excludes the project's Node is held as `engines: needs node <target> (the project declares <range>)`. The declared range is the owning manifest's `engines.node` (a member's own, else the root's; `declaredNodeRange` keeps only a real constraint, `*`, `x` and `>=0` declare nothing, and an invalid value logs a debug line naming the file), and every Node it allows must fit the target (`semver.subset` with `includePrerelease`). With nothing declared the running Node is judged (`semver.satisfies`, `includePrerelease`): `(running node <v>)`, or `(pnpm nodeVersion <v>)` when the adapter's `nodeVersion(cwd)` answers (`FilterPackagesOptions.node` / `nodeLabel`, passed by `plan`). Under a Bun runtime (`runningNode()` null) with nothing declared the row is skipped, with one debug line. A target with no `engines.node`, or `*` / `>=0`, moves; an unknown manifest moves and joins the plan's unknown-manifest warning. A `latest` rule moves it with the text as `warning`. Probed 2026-11-07: npm 11.19.1 judges engines by the running Node only, pnpm 12.18.0 by `nodeVersion` when set else the running Node, bun 1.4.4 ignores engines; none judges by the project's own `engines.node`, so the declared-range hold is autd's own signal. Limitation: a target of touching pieces (`^22.12.0 || >=23`) against a declared `>=22.12.0` is held though it covers it, since `semver.subset` does not join adjacent ranges
- **Target peers** (`targetPeerConflict`, #198), inside the last `settle(rows, targetPeers)` of `signals` (after `holdPeerConflicts`, before `holdTogether`), only when the manifests map is non-empty: for each moving row's target manifest, each `[peer, range]` (own name skipped; a range `semver.validRange` rejects, e.g. `workspace:*`, skipped with a debug line) is checked, with `includePrerelease`, against the version the plan leaves that peer at: its row in the same manifest (target if moving, else current unless `missing`), else the root's row from a member, else the installed version (`FilterPackagesOptions.installed`, called once per plan; default `readInstalledVersions(cwd, rows, { declaredOnly: false })`; the pipeline passes the lockfile reader when `adapter.installedFromLockfile` answers: npm without `node_modules`, berry PnP). A peer found nowhere is fine: optional (`optionalPeers`), or left to the manager with a debug line. A miss holds the row as `peer conflict: <name>@<target> needs <peer> <range> (installed <v>)` or `(moving to <v>)`, in the existing `peer` report outcome. A `latest` rule moves, and the warning is added once the plan is stable. Matches npm (ERESOLVE), stricter than pnpm and bun, which only warn or accept (probed 2026-11-08)
- **Held together**: a workspace record expands to one `UpdateResult` per (package, manifest) (`expandWorkspaces`), each with `workspace`; single-package results have no `workspace` key. `holdTogether` (`settle.ts`) holds a package's moving rows whenever another row of it is held while its range allows newer (`held with <path> (<reason>)`), because the in-range commands are workspace-wide; an exact pin blocks nothing. The peer pass and `holdTogether` repeat until nothing changes (`settle`), once before the cooldown and again after it, so a row held by either, or by the cooldown, stops counting as moving for the peer check. yarn v1 moves a member's packages with root installs (`pinMembers`, #127), so it holds the same way

## `splitUpdates`

`splitUpdates(results)` also returns `manifests` (`ManifestPlan[]`, root first, then by path) and divides the chosen updates into `withinRange` names (target == wanted: hand to the manager, write nothing) and `beyondRange` name → version (write the manifest spec first). A row whose target is neither `wanted` nor `latest` (a cooldown fallback, an engines walk-back) is `pinned` (`PinnedRow[]`), and so is every other moving row of its package; with `{ pinMembers: true }` (the adapter's `pinMembers`, yarn v1, #127) so is every moving row of a package that moves in a member; `names` and `manifests` leave pinned rows out, and `src/managers/pin.ts` applies them first. `checkApplied` (`installed.ts`) then wants every row of a package with a cooldown fallback installed at exactly its target, since a newer version is one the cooldown held (#151).
