# The human report and `--json` rows

Reference for `src/utils/report.ts`, `logger.report`, `reasons.ts` and `jsonDocument.ts`'s rows. `src/utils/CLAUDE.md` links it; nothing imports it. Read it before changing a report section, a note, a reason or the row shape. The document around the rows is in `src/commands/CLAUDE.md`.

## What prints (#138)

`check`, `update --dry-run`, interactive and `update` print one report (`logger.report(results, manager, phase)`): each planned row once, under its outcome (`groupResults`: would update / updated, left in place, held by cooldown, past the range with the `beyondRange` level that would move it, held by a rule, an override, a peer conflict, as deprecated, for a license change, for engines, with another manifest), rows sharing a move and reason across manifests merged, then one summary line. `update` prints it after apply only (`phase: 'applied'`); before apply only `Updating N packages with <pm>`. A workspace of one manifest prints no workspace line or manifest column, and neither does a member run (#123): `logger.memberRun(manager, path, count)` has printed `<pm> workspace member <path> (1 of N manifests)` first, and `logger.report`'s `{ member }` option (the member's path) drops the column whatever the rows hold. `--json` prints the document from the same rows; `check --json` plans through `findOutdated` and `plan`, so its rows are the ones the report groups.

## Sections and notes (`report.ts`)

- `outcomeOf(result)` files an `UpdateResult` under `update` when it moved, else by `reason.code` through `SECTION_OF: Record<ReasonCode, Outcome | undefined>` (exhaustive, so `tsc` fails on a code with no section; `not-targeted` maps to `undefined` and is left out). No prefix matching on `reason.message`. A new reason needs a code in `reasons.ts` and a section in `SECTION_OF`
- `groupResults` merges rows that share name, versions and note across manifests, sorts by name then root first, and orders sections update → left in place → cooldown → outside the range → rule → override → peer → deprecated → license → engines → held with → other
- A moving row's note is empty within its range (the default), `rewrites its range` past it in the plan and `range rewritten` once applied (`groupResults(results, phase)`; a row whose spec is a `catalog:` reference, `UpdateResult.catalog` (set by the pipeline's `plan` through `catalogOf`, report only), says `rewrites its catalog entry` and its manifest column reads `catalog:<name>`, one row for every manifest using it), with the notes joined by `NOTE_SEPARATOR` (a `·` with a space either side). A row whose `wanted` sits below `current` (a deprecated version installed) shows no in-range note
- A hold that cleared a target keeps it as `UpdateResult.judged` (cooldown, peer, target peers, deprecation, license, engines, held with, override, not applied; set by `heldFor`, the cooldown hold, `holdTogether`, the override hold and `checkApplied`), and the report shows `target ?? judged ?? latest`, colored by the step from `current` to that version, so the version, its age and its note describe the same release (#221); `judged` is not in `--json`, whose `updateType` is unchanged
- A held row past its range shows its step (`major`), and the section's `hint`, on its own line, names the `beyondRange` level and `.always-up-to-date.json` once (`rangeHint`: `"beyondRange" in .always-up-to-date.json: "minor" would allow 1, "major" all 3` when the steps differ). It says "allow", not "move": the report sees the plan's rows, and the passes after the policy can still hold a row the level lets through, which only a plan run at that level would show
- A `latest` rule's `warnings` are `ReportRow.warnings`, printed yellow behind `!` after the note. The release-age tail uses `formatAge` (years past 365 days: `7.6y`); `formatAgeDays`, which reason messages and so `--json` carry, stays in days. `ReportRow.level` is the row's `updateType`; `formatRow` colors `to` from `splitAtChange(current, to)` (red major, yellow minor, green patch or unknown) and leaves `current` plain
- `logger.report`'s `next` (from `check` and `--dry-run`, built by `commands/actions/applyCommand.ts`: `autd update`, the targeted names, then the run's `--pm` and `--no-cache`) prints `Run <next> to apply.` when something would move (`in the workspace root` from a member), and `elapsedMs` (applied `update`, from `pipeline.update`) ends the summary line with `(took 12.3s)` (`formatElapsed`)
- A moving row with code `engines-fallback` (npm's walk-back, #200) stays under update, and its note adds the stripped message (`5.1.6 needs node >=14.17 (running node 12.22.12)`); `cooldown-fallback` adds `<version> held by cooldown (<age> old, needs Nd)`

## Reasons and rows (`reasons.ts`, `jsonDocument.ts`)

- `reasons.ts`: `OUTCOMES` and the 21 `REASON_CODES` (`ReasonCode` in types.ts derives from them); imports nothing, so anything may import it (#201)
- `UpdateResult.reason` is a required `Reason { code, message }`; `warnings?: Reason[]` replaces a single warning (a `latest` rule moving past a peer conflict, deprecation, license change or engines hold)
- `jsonDocument.ts` maps a row to the `--json` shape (`rowOf`): `outcome` is `update` when `updated`, `not-applied` / `not-targeted` by code, else `held`; `current: 'missing'` becomes `null`, `workspace` defaults to `"."`, `target` and `releaseAge` become `null` when absent
