# Registry, `.npmrc`, reader and cache

Reference for `src/utils/npmrc*.ts`, `registry*.ts`, `reader*.ts`, `releaseAgeGate.ts`, `redaction.ts`, `limiter.ts` and `errorFields.ts`. `src/utils/CLAUDE.md` links it; nothing imports it. Read it before changing how autd reads a manager's registry settings, asks a registry, or caches an answer. Each manager's own files and precedence are in its Tier 3 doc: `src/managers/{npm,pnpm,yarn,bun}/CLAUDE.md`.

## `.npmrc` parser and layers (`npmrc.ts`, `npmrcLoader.ts`)

- `parseNpmrc(text, env, substitute?)` is ini 7's decode (quoting, `;`/`#` cuts, `key[]` arrays, parsing stops at the first `[section]`, `__proto__` skipped) plus a `Substitute` on keys and values, npm's by default (an unset `${VAR}` stays literal, `${VAR?}` is empty, `\${VAR}` is escaped); null leaves them as written
- A manager's `.npmrc` view is a list of `NpmrcLayer`s, highest first (`{ kind: 'env' | 'file', values }`), which `mergeNpmrcLayers` merges per key: the first layer that sets a key wins, whatever its type, and `view.origin(key)` names that layer (`NpmrcView`). `envLayer(env, rule)` reads variables by an `EnvRule` (`prefix`, `key(rest, name)` where undefined skips the variable, `substitute`; empty values skipped); `npmrcFileLayer(file, env, { substitute, omitReferences })` reads a file; `substitute: null` expands nothing, and `omitReferences` leaves out an entry whose key or value still holds `${…}`, so a lower layer decides. An `EnvRule`'s optional `rank(name, key)` picks among variables naming the same key (higher wins, later in `env` among equals). `NpmrcSources` (env, home, execPath, platform) is injectable for tests; a layer never throws, an unreadable file is empty
- `ManagerAdapter.npmrcLayers?(cwd, sources)` supplies the manager's own layers, highest first; without it, `npmNpmrcLayers` (npm's, `src/managers/npm/CLAUDE.md`). pnpm, bun and yarn v1 have their own (`managers/pnpm/npmrc.ts`, `managers/bun/npmrc.ts`, `managers/yarn/npmrc.ts`); yarn berry reads no `.npmrc` (no layers; #107)
- `ManagerAdapter.registryConfig?(cwd, fromNpmrc, sources, npmrc)` adjusts the `.npmrc` view for a manager that routes registries elsewhere too; `npmrc` is the merged `NpmrcView`. `managerRegistryConfig(adapter, dir, sources)` is the session's wiring: the merge of the adapter's layers, `registryConfigFrom`, then the `registryConfig?` hook. `openProject` passes the session a `loadConfig` that does this, so it still reads nothing until the session's first `registryConfig()`. The adapter returns the final config, so each encodes its manager's precedence (verified on pnpm 12.15.0 / bun 1.4.4, 2026-10-26). yarn v1 (`.yarnrc`) and bun (`bunfig.toml`, `BUN_CONFIG_*` / `NPM_CONFIG_*` registry and token variables over `.npmrc`) add their own registry files through it; berry builds its whole config there from `.yarnrc.yml`; pnpm builds its whole view as `.npmrc` layers, its yaml routes included, with no hook
- `npmrcLoader.ts` uses `@/managers/workspaces` to find the npm project root (no cycle: `workspaces.ts` imports only the logger and `managers/pnpm/workspaceYaml.ts`, which imports only `yaml.ts`)

## `RegistryConfig` (`registryConfig.ts`)

- `registryConfigFrom(npmrc, cwd, sources)` builds `RegistryConfig`: registry and `@scope:registry` (`scopedRegistries`), `credentials` by `//host[:port]/path/:` prefix (`_authToken`, `_auth`, `username` + `_password`, `certfile` + `keyfile`), `ca` / `cafile`, `strict-ssl` (`strictSSL`), proxy (`https-proxy`, `proxy`, `noproxy`, environment fallback), `fetch-retries`, `fetch-timeout`, `maxsockets` (`maxSockets`). Unscoped `_authToken` and `always-auth` are ignored, as npm 9+ does; yarn v1 reads both (`yarnV1Auth`, `src/managers/yarn/CLAUDE.md`)
- An unusable registry value (a URL that does not parse, a non-http(s) one, one holding `${…}` or, in its host, a `$`, an empty one; npm 11.19.1 fails on `https://${UNSET}/` with ENOTFOUND) is not skipped where the manager fails on it. `registryConfigFrom(view, cwd, sources, empty?)` (the `NpmrcView`, so each value is named by its layer; a layer's optional `labels` give the key as the source spells it: the variable, `registries."@acme"`) leaves it out of `registry` / `scopedRegistries` and records it in `RegistryConfig.unusable` (`registry`, `scopes`: `{ key, value, source, reason }`, the value shown by `describeUnusable`: `<scheme>://<host>/` with a path behind `pathMarker`, userinfo and query never shown; a value with no scheme and host is `(value not shown)` unless it is only `${NAME}` references). `unusableRouteFor(name, config)` gives the one a package is routed through (its scope's, else the default's, unless a usable scope route covers it); the session itself refuses such a package (`releaseTimes` returns `{}` with a debug line and sends nothing; `lookup` answers `invalid`), and `discoverFromRegistry` asks `session.unusableRoute(name)` first and throws a `discover` `StepError` (`<pm> can't use <key> \`<value>\` from <file>; fix or remove it`) instead of asking another registry. Only the winning value counts: a bad value a higher layer shadows is not an error
- Verified 2026-10-27 (npm 11.19.1, pnpm 12.15.0, yarn 1.22.22, bun 1.4.4, each with `install`): all four fail on an unparseable URL, text, `ftp://…` and an unset `${VAR}` as the default or a scope route (a scope route only when a package of that scope is resolved), in `.npmrc`, the environment and the manager's own file (bunfig.toml, pnpm yaml, `.yarnrc`). The exception is pnpm, which skips a `${…}` in a project file (`.npmrc`, `pnpm-workspace.yaml`) and falls through, as autd does; a `${VAR}` that pnpm's global files expand to nothing is an empty value, which pnpm fails on. Empty values differ and are the adapter's `emptyRegistry`: npm fails on an empty default and skips an empty scope, pnpm fails on both, yarn and bun skip both. Not mirrored: yarn also fails the whole run on an unset `${VAR}` in a shadowed `.npmrc` registry line

## Session (`registry.ts`)

- `openProject` makes one `RegistrySession` per run (`Project.registry`), its `.npmrc` view loaded at the project root, where every manager command runs, whatever the cwd (#127): `registryConfig()` reads the `.npmrc` layers and `cafile` on its first call, `client()` creates the one `node:https` client, so every registry request in the run shares both. A session reads and loads nothing until asked; `close()` warns once when a host answered 429 during the run (`throttledNotice`: `Throttled by <host> (<n> requests), …`; #174; on stderr under `--json`, nothing under `silent`), since the fallbacks keep the results correct and only the time would show it, destroys the agents (safe twice, or before any request), and commands call it in a `finally`. `loadConfig`, `clientOptions` and `endpoints` are test seams; `depsDev` is the config switch
- `registry.ts` imports `registryClient` with `await import('./registryClient')` on the first request, so the client loads with the first request, not when a command starts, and `--version` and `help` never load it (`__tests__/startup.test.ts` guards this); keep top-level imports there to types, `registryRequest`, `registryUrls`, `npmrcLoader` and `logger`. `registryReader` (with its parts, `reader*.ts`), `registryDocuments` and `limiter` load only through `await import()` from the session, so no lookup's cost lands on the CLI's startup; `registry.ts` gains no top-level import of the cache or reader. `__tests__/startup.test.ts` mocks `@/utils/registryCache`, the reader and the client and proves none loads with the CLI; the build's startup check (`scripts/guards.ts`) guards the same on the bundle
- The reader's own per-session map holds the in-flight request, so a package several workspace manifests declare is fetched once; a new session asks again. The session keeps each name's answer too, and `session.lookedUp(name)` returns it (undefined before the first lookup; it never loads the reader or sends a request), which the plan's deprecation pass reads (#195). `withReleaseAgeGate` gates each name once per session and its `lookedUp` returns the gated answer

## Client (`registryUrls.ts`, `registryAuth.ts`, `registryRequest.ts`, `registryClient.ts`)

- The first three are the pure part of the client (registry per scope, packument URL; longest-prefix credential lookup, yarn v1's and berry's credential rules, Authorization header; retry rules); `registryClient.ts` is the `node:https` transport (keep-alive agent per registry, gzip, timeout, retries with `Retry-After`, redirects that recompute credentials). SOCKS proxies are not supported
- The client sends credentials only to the longest `.npmrc` prefix that matches the request URL, and recomputes them on each redirect (yarn v1 and berry have their own rules: `src/managers/yarn/CLAUDE.md`). Retries cover 408, 420, 429, 5xx, ECONNRESET, ECONNREFUSED and ETIMEDOUT with a short capped backoff; a `Retry-After` over 1 s stops retrying
- `getJson(url, registry, { signal, accept, timeout, retries })`: `accept` defaults to `application/json`, `timeout` to `fetch-timeout` (ms), `retries` to `fetch-retries`; all hold across redirects and retries. The reader sends deps.dev requests with `retries: 0`. `stats()` returns copies and counts per `url.host`: `responses` (every status), `throttled` (the 429s among them, a retried request's each), `bodyBytes` (2xx bodies as received) and `decodedBytes` (after gunzip)
- URLs in messages: a `request` reason is the client's message, which carries the URL as `describeUrl(url, registry)` shows it: the origin, then `/…[3fa9c1]` for the registry's own path (a token can sit there, as in Gemfury's `https://npm-proxy.fury.io/<TOKEN>/<user>/`), then the rest: `https://npm-proxy.fury.io/…[3fa9c1]/left-pad`. The marker is the first 6 hex characters of the SHA-256 of the registry path (`pathMarker`), so one registry always shows the same marker and two registries on one host differ. The public npm registries and deps.dev, and a registry at the origin root, show whole. A redirect target (`{ redirect: true }`: every hop after the first, and the target of a refused redirect) and any URL outside the registry path show the origin and `/…`. Never userinfo or query; an unparseable URL gives `(invalid URL)`, `describeUrl` never throws. The client words every failure through its one `requestError`, so no site formats a raw URL
- Text from outside autd gets the same treatment from `redaction.ts` (#131): `openProject` calls `trackRegistries(() => session.registryConfig())`, and `scrub(text)` (built on first use, so a run that prints no URL reads no `.npmrc`) replaces each configured registry (default and scopes) whose path is not the root, as a URL and in its `//host/path` nerf-dart form, with the same `…[marker]` form. The logger's `diagnostic()` (warn, error, debug, command) and `reportFailure` (human and `--json`) are its only exits, so a manager's stderr that prints the registry URL is scrubbed in the debug line and the `StepError` message

## Lookup (`registryReader.ts`, `readerLookup.ts`, `readerDepsDev.ts`)

`session.lookup(name)` (loaded with `await import()` on the first call) returns a `PackageLookup`: `ok` with `{ name, latest, versions, source }` (each version has `deprecated`, and `publishedAt` when the source has it), or a failure `{ ok: false, kind, reason }`, and never rejects for a network, HTTP or parse failure, never "no versions" for a network failure. Discovery (`src/discovery.ts`) is its consumer.

- An invalid name (`isValidPackageName`) is `invalid` with no request. A public npm name (registry root is `https://registry.npmjs.org/` or `https://registry.yarnpkg.com/`) fetches `/-/package/<name>/dist-tags` and deps.dev together. When deps.dev lists `latest` the result is `source: 'deps.dev'`; otherwise (deps.dev 404, 429, 5xx, unreachable, unreadable, or `latest` missing) the abbreviated packument is read, and every version it lists that deps.dev also lists gets deps.dev's `publishedAt` (`withTimes`; `source` stays `'packument'`, and the version list and deprecations stay the packument's), so only the newest versions deps.dev has not indexed lack a time. A dist-tags 404 is `not-found`; any other dist-tags failure takes the packument path, a 429 included: the results stay correct, and the run says so at `close()` (#174)
- Any other registry, a scope's registry, or `depsDev: false` takes one GET with `ABBREVIATED_ACCEPT`, retried once with `application/json` on a 404 (as pacote does). The packument wins when it lacks the dist-tags' `latest`: the packument's own `latest` is used, else the highest stable version
- deps.dev: only names on registry.npmjs.org or registry.yarnpkg.com are ever sent to it, and it gets only its own URL as the client's registry base, so no `.npmrc` credentials go to it. A 429 or a timeout turns deps.dev off for the rest of the run (one debug line). Any other 5xx or transport failure falls back to the packument for that package only, and the third such failure in a run turns deps.dev off; a 404 does not count. The decision is made inside the failed request's limiter slot, before the next queued request starts. deps.dev requests time out at `min(fetch-timeout, 5 s)` with no retries (the 5 s is the reader's `depsDevTimeout` option, which tests lower), and a request still queued when the breaker trips is skipped once it reaches the front
- Requests go through one limiter per host (`new URL(url).host`, `limiter.ts`), each of `maxsockets`, the client's per-host agent cap: a queued request never waits in an agent queue and burns its timeout, and only that many packument bodies per host are buffered at once. With two hosts (dist-tags and deps.dev), up to `2 × maxsockets` requests are in flight; measured 2026-10-26 on the 40-package benchmark, lookups took 0.57–0.70 s against 0.75 s with one run-wide limiter
- A body the client cannot parse as JSON is a `request` failure; a JSON body that is not a packument is `invalid`. `not-found` and `invalid` reasons name the registry's host
- `RegistryPackage.modified` (#177): the abbreviated packument's top-level `modified`, an upper bound on every listed version's publish time (verified on the 40 packages of `bench/pinned/`, 2026-11-06). The reader sets it only for a packument read from a public npm registry (`isPublicNpmRegistry`: other registries, scope routes and a full document, whose bound is `time.modified`, get none), so the gate needs no knowledge of registries

## Publish times (`readerReleaseTimes.ts`)

`session.releaseTimes(name, window?)` (for cooldown and the release-age gate, #47) refuses an unusable route (`{}`, nothing sent) and otherwise calls the reader's `releaseTimes`, which never rejects. Cooldown's network path (`releaseTimes`, npmrcLoader) never throws: a transient error leaves the times the lookup had (an empty map when it had none).

- It looks the name up with the reader's memoized `lookup` (a failed lookup is `{}`, no request), takes that lookup's `publishedAt` as the times (deps.dev's, which a lookup that fell back to the packument keeps for every version deps.dev lists, and a packument's own `time`), and asks for the full packument (the abbreviated one has no `time`) only when `window` judges a version still without one: the versions above `window.current`, up to and including `window.target` (`{ current, target }`, so the target and every cooldown fallback; every untimed version with no window, as the gate asks, or when either end is not semver, e.g. a `missing` row). `filterPackages` skips the call for a step whose cooldown is zero days
- The request is `get` + `revalidate` on the package's registry, through the same credentials, so it takes the host's limiter slot, and the answer goes through the `packument-full` cache, memoized per name per run (the untimed versions are the same on every call). Its times win over the lookup's, only for versions both the document and the lookup list (a `time` entry of an unpublished version, `created` and `modified` are dropped, and so is a version a stored document still lists after an unpublish), so an unpublished version's `time` entry never becomes a fallback. A failed or unreadable document, or any throw while reading it, keeps the lookup's times with a debug line; the cooldown gate holds a target with no known time (`cooldown: release date unknown, requires Nd`; a lagging mirror or proxy drops fresh versions, #139), since the freshest releases are the ones a lagging mirror lacks
- The debug line, logged after the response and naming the judged versions that caused the request, tells them apart (#176): `Reading the full packument of <name> for publish times: …` when a body came back (the bench's `fullPackumentReads` counts it), `Revalidated the full packument of <name> for publish times (304): …` when none did. A failed request has its own line, and a cache answer logs none: a stored document past its TTL that the coverage rule answers counts as `covered` in the run summary

## Version manifests (`readerManifests.ts`)

`versionManifest(name, version)` (#196) returns the version's own `VersionManifest` (license, `engines.node`, peers, optional peers, `dependencies` and `optionalDependencies`, deprecation) or `undefined`, and never rejects: one GET of `versionManifestUrl`, parsed by `parseVersionManifest` incl. legacy `license: { type }` / `licenses[]`; memoized per pair per run (failures included); no request for an invalid name, a non-canonical version, a failed lookup or a version the lookup does not list; through the same limiter and credentials; the lookup's deprecation overlays the document's, and a 404, failure or unreadable document is a debug line. The session refuses an unusable route with a debug line, and `withReleaseAgeGate` forwards it ungated. `filterPackages` reads it (`src/utils/targetManifests.ts`) only for rows still moving after the deprecation pass, so an all-held check sends no per-version request (discovery alone, `findOutdated`, reads none; `check` and `check --json` plan, so they read the moving targets' manifests, cached).

## Disk cache (`registryCache.ts`, #108)

- The session loads it with `await import()` only when `openProject` turned it on, never at startup. The session's `cache` option (`{ dir?, now?, maxBytes? }`) is none by default, so tests and `--no-cache` / `AUTD_NO_CACHE` (anything but empty, `0`, `false`) touch no folder and do not even resolve it. The session builds the cache with the reader (`cacheDirectory(cwd, processSources())` when no `dir`). A session closed while the reader's imports were pending makes no cache
- Where: one gzipped file per answer under `v1/<kind>/<sha256>.json.gz` in `ca.pixel-perfect.alwaysuptodate`, i.e. `~/Library/Caches/` on macOS (`XDG_CACHE_HOME` has no effect), an absolute `$XDG_CACHE_HOME` else `~/.cache` on Linux, `%LOCALAPPDATA%` (else `<home>\AppData\Local`) on Windows, or `AUTD_CACHE_DIR` (against cwd). An entry holds the hash of its key, never the endpoint (a registry path can carry a token); `CACHEDIR.TAG` sits in `<dir>/v1/`, never in the folder `AUTD_CACHE_DIR` names. Deleting the folder is always safe
- What: the parsers' outputs (dist-tags `latest`, deps.dev versions, packument versions), never a body, a header value or a credential. Entries hold `Cache-Control` and `authenticated`
- Kinds and default TTLs (`TTL_SECONDS`): dist-tags 300 s, deps.dev 3600 s, packument, packument-full and manifest 300 s, lowered by `Cache-Control: max-age`; `no-store` is not stored; `no-cache`, `max-age=0` or `private` revalidate every use. `Age` counts against the TTL, and a 304 keeps the stored `Cache-Control` unless it restates one
- `freshFor(kind, meta, sameForEveryone)` decides the TTL: 0 means only after a 304 (needs an ETag), undefined means not stored. The response decides what an authenticated request may reuse (Q1 a): served without asking only if `sameForEveryone`, i.e. for dist-tags deps.dev lists the package (`Cache-Control: public` alone does not count, since a private registry may send it; `private` always revalidates); otherwise stored only with an ETag and revalidated every use
- The reader's flow: a fresh dist-tags and deps.dev entry answer with no request and no client; a fresh deps.dev entry that lacks the dist-tags' `latest` gives way to a fresh packument entry that lists it, also with no request and no client, so a package deps.dev lags on doesn't cost a warm run the client, and with no such entry deps.dev is asked once more before the packument; a packument past its TTL is revalidated with `If-None-Match` (a 304 refreshes it); a fresh packument entry that lacks the dist-tags' `latest` is revalidated, not trusted; a registry that serves only the full document keeps that entry and is asked nothing while it is fresh. `depsDev: false` reads and writes no deps.dev entry. Cache reads and writes run outside the limiter slots
- Publish times (`releaseTimes`, #47) read and write the same `packument-full` entry (same key, same document) by a coverage rule instead of the TTL: an entry listing every version the lookup still lacks a time for answers whatever its age, since publish times never change (a version it lists without a time is a known gap; one it does not list means the entry predates it, and the registry is asked with the stored ETag (`If-None-Match`), a 200 replacing the entry), except that an authenticated entry, or one stored under `private`, `no-cache` or `max-age=0`, is revalidated on every use (a 304 costs no body). A fresh entry written there can also answer a lookup that has no abbreviated one
- A `manifest` entry (a target version's own document, #196; TTL 300 s, key `<name>@<version>`) is reused whatever its age too, since npm never republishes a version, with the same exceptions (`revalidatesEveryUse`: authenticated, `private`, `no-cache`, `max-age=0`), except that an authenticated answer counts as the same for everyone when deps.dev lists the package (`sameForEveryone`, Q1 a, as for dist-tags: the lookup's `source` is `deps.dev`), so a token for registry.npmjs.org doesn't stop it being stored. npmjs sends `max-age=300` and no ETag, so an authenticated manifest of a package deps.dev doesn't list is not stored and is asked again each run; Verdaccio sends an ETag, and a 304 revalidates. A stored manifest must carry `dependencies` and `optionalDependencies` (records of strings, which the peer pass reads): one stored before they were kept fails `validValue` and is read again once, with `SCHEMA` unchanged
- `modified` (#177): the cache keeps it whatever the registry (`validValue` only requires a string when present; `SCHEMA` is unchanged, an entry without it simply takes no shortcut), so trusting another registry later needs no bump
- Fails open: an unreadable entry is a miss, an unwritable folder stops writes for the run with one debug line; lookups still report failures, and a failed request never falls back to a stale entry
- Size and writes: capped at 32 MiB by LRU mtime pruning at `close()` when the run grew the folder, and written atomically (temp file, rename). `close()` logs one debug line (fresh / covered / revalidated / fetched / written / pruned, and requests per host, `none` when no client was made), then destroys the client. Known cost: `close()` scans the folder after any growth (about 8,000 stats at the cap, tens of milliseconds)

## Release-age gate (`releaseAgeGate.ts`, #166, #168)

A manager's release-age gate beats everything, as autd never overrides a manager's security setting: `RegistryConfig.releaseAgeGate`, applied by `withReleaseAgeGate`, wrapped around the session by `openProject` and reading the gate on the first lookup, so no version the manager refuses for its age is proposed. Each adapter reads its own through the `releaseAgeGate(cwd, sources, npmrc)` hook, which `managerRegistryConfig` sets on the config (berry in `berryRegistryConfig` instead); the per-manager settings and probes are in the Tier 3 docs, and each probe is a case in `__tests__/releaseAgeGates.test.ts`.

- A lookup keeps only versions published at least the gate's minutes ago (or exempt), `latest` moves to the highest stable one below it that passes, and no version let through is a `quarantined` lookup, which discovery leaves out with a warning. Times the lookup lacks come from `releaseTimes` for every version (the full packument read once per name per run and kept in the registry cache). `releaseTimes` keeps only passing versions' times and forwards a cooldown's window, so a cooldown fallback never lands on a quarantined one. So neither `wanted`, a past-the-range target nor a cooldown fallback is a version the manager quarantines
- A version with no publish time: pnpm, bun and npm let it through (`missingTime: 'allowed'`); berry holds it (`missingTime: 'held'`), as berry treats it. Exemptions are `ReleaseAgeExemption { name, glob, versions? }`
- `modified` shortcut (#177): `withReleaseAgeGate.lookup` skips `session.releaseTimes` when some version has no time and `modified` clears the gate (`clearedByModified`: the gate's `missingTime` is `allowed`, and `modified` is at least the scope's minutes old and not after `notAfter`, both inclusive), with a `No publish times needed for <name>` debug line: a version with no time then passes, and one with a time is still judged by it, so a `modified` that isn't a true bound can't let through a version whose time is known. So a cold `check` reads the full packument only for the packages modified within the gate. Berry and pnpm with `minimumReleaseAgeIgnoreMissingTime: false` never take it. A missing, unparseable or future `modified` takes the read. `withReleaseAgeGate.releaseTimes` and cooldown are unchanged: a cooldown still reads exact times for its moving rows
